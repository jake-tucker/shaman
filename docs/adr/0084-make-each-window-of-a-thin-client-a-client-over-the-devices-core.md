# Make each window of a thin Client a Client over the device's core

_Follows ADR-0080, which put a thin Client's protocol code in one Rust core the app opens once, and ADR-0081, which keeps its identity on its device. Decided in #721, on the findings of #711, and built in #764. Numbered 0084 because 0083 is already taken on another branch, `feature/desktop-app-full-client`, which has not reached main yet._

A phone can show a thin Client in two windows at once: on an iPhone Duo a person docks the app to one side and opens it again in the other half, and the system makes the second window, which the app neither offers nor arranges. Until now the two shared everything the core held, so narrowing the listing in one narrowed the other, and opening a Session in one turned the Outlook a first Prompt was being written for in the other.

So each window of a thin Client is a Client of its own, as two TUIs on one machine are, over the device's core, which plays the part a Server plays for those TUIs. The core is split in two. The device's half is opened once for the app and holds what is the phone's: the identity key and the device's name, the Pairings, relay logins and connections, what each Remote says (Sessions, conversations, trees, Interventions), the front, background time and the network path, and every draft. Each window asks it for a window's half, which holds what a Client holds for itself: the Outlook and the Workspace it stands at, the listing's scope, its search and how much of the settled shelf is up, the Landing and what it says, a Workspace Picker's search, and which notices it has said. A Serving Server still knows the phone as one Peer, however many windows it shows.

- **Nothing done in one window turns the other's Outlook.** Opening a Session, narrowing a listing, choosing in a Workspace Picker and pairing each turn the Outlook of the window they were done in. A first Prompt written in one window begins where its own screen says, whatever is opened beside it.
- **A new window begins where the phone was last turned, by any window,** at the Workspace remembered there, with its listing at Everywhere. The Workspace remembered for each Remote is a window's own while it lives; the phone keeps the latest turn of any window in its records, which is where a new window and the next launch begin. A window that stands at no Remote of its own, as one made before the phone held any, comes to stand at the first it can and stays there whatever another window turns toward after.
- **Drafts are the device's, and nothing is built beyond the one kept draft.** One is kept for each Session and one for the new-session screen. Each field holds its own text while it stands and never takes another window's typing; what is kept is whichever was written last, and a field opening later starts from that. A Prompt the core gives back, one whose send failed or that a stop withdrew, lands in every field of that Session, since the core cannot say which window sent it, each putting it ahead of its own text and not of what another window wrote. The core tells each window whether the text kept was last written there, so that a screen shown again, as one is on Back from a Turn's work, takes what another screen of its own window wrote meanwhile, as one window always has, and never another window's.
- **A Questionnaire's half-given answers are the device's too, in memory alone.** The core keeps them for as long as it runs, by Session and Questionnaire, and never in its directory. They follow the same rules as a field's text: a sheet holds its own while it stands, and one opening later, in either window, starts from whichever sheet changed them last. A secret's answer taken from there shows nothing of itself, as its reader left it. This was a judgement, where the ticket's two sentences pulled apart: the half-given answers "behave the same" as drafts, yet "nothing is built beyond today's" drafts. They behave the same, and nothing is written beyond today's file.
- **A notice is each window's to say.** A Remote found newer than the app is said once in each window, a window made later included, as long as the phone still holds it and by the name it goes by now, and seen in one it stands in the other until it is seen there. A Pairing ending is said in each window whose Outlook stood there, which turns to the Remote the phone was most recently turned toward that is still held; a window whose Outlook stood elsewhere is turned by nothing and says nothing. Where no window's Outlook stood there, what the phone is still to hear, that the Remote removed this phone or may still list it, is said once, by the oldest window that stands, so an ordinary iPhone's one window says what it said before there were two, and two windows never say it twice; an acknowledged removal there says nothing, as it did. This was a judgement in #765, where "says nothing" would otherwise have left a removal the Remote never heard of unsaid on every phone. One that ends while no window lives yet, as the core opens before the app asks for its first window, is kept by the device and said by the first window to stand, as it first follows what the core says, and by no other.
- **Each window presents an Intervention by itself.** Each reads the Session for itself, so an answer in either takes it down in both, and a swipe is that window's own.
- **What is open, sheets, a conversation's place and the Aside's two values were each window's already,** as the scene's and the window's own state.

## Considered Options

- **One window only**, by turning the declaration of several scenes off. Rejected: a second window works on the phone today, and turning it off takes it away for nothing.
- **One Outlook for the phone, held still while a new-session screen is open in another window.** Rejected: it keeps the shared Outlook's surprise and only hides it at the one moment it is most felt, and it ties the windows together in a way two TUIs never are.
- **Drafts each window's own.** Rejected: a window can be swiped away or discarded by the system at any moment, and text written on a phone must not be lost with it. Typing in one field showing in the other was also rejected, as no TUI does that and it would surprise whoever is typing.
- **A second window the app offers, or two conversations in one window.** Rejected in #721: the first rests on what nobody has verified of how a Duo tells an app a window can be made, and the second would be a fourth thing on a display the system tiles two columns across.

## Consequences

- The Swift app reaches the core through two protocols, the device's and the window's, with the live core and the fake split the same way. The app opens the device's once, and each window's root asks it for a window as the root is first drawn, never as SwiftUI makes it, which it may do more than once and throw all but the first away.
- Each Landing up has its own Workspace resolved, so two windows' Landings on one Remote do not take each other's.
- A window's own state lives only while the window does; the scene's storage is what brings any of it back after a cold start. The kept scene holds the window's Outlook, its Remote by its key and the Workspace by its path, beside its scope, and hands both back; handed back, an Outlook is not the phone's latest turn, and one whose Remote is gone stands where a new window would. Launch arguments act in the first window drawn alone (#765).
- Nothing automated opens two windows: the core's tests hold two windows over one core, and the pair itself is a check on the phone.
