# Move a Session's Execution Directory rather than beginning another Session

ADR-0023 fixed a Session's Execution Directory from its first Turn: a user who wanted the same work to continue elsewhere — in another Worktree of the Repository, in a Worktree made for it, in another Workspace — began another Session and lost the conversation. We decided that a Session may **Move**: its Execution Directory changes and everything else about it stays — identity, Title, Icon, Transcript, and the Provider conversation, which resumes in the new directory at its next Turn the way ADR-0058 already resumes it after an idle stop. All three Providers resume a conversation in a directory other than the one it began in (Codex and Copilot take the directory on resume; the Claude CLI was tested to resume under the same ID from another directory), so no Provider needs a copy made for it.

The Session's Execution Directory is still fixed while a Turn runs, because the Provider's process is bound to it. A Move asked meanwhile is therefore **pending** and takes effect when what runs in that process settles; a Monitoring Session Moves at once. A newer pending Move replaces an older one, choosing the current location cancels it, and a Managed Worktree a pending Move asked for is created when it is asked for, not when it applies, so a Tool call learns of a failed preparation in its answer.

## Considered Options

- **Begin a new Session in the destination and carry context across.** Rejected: the conversation is the thing the user wants to keep, and no Provider lets one be copied into another cwd more faithfully than resuming it there.
- **Refuse a Move while Working, and have the user interrupt first.** Rejected once Agents could Move their own Session through the Broker: an Agent is Working whenever it calls a Tool, so refusing would make the Tool useless for exactly the case it exists for. One deferred rule serves the TUI and the Broker alike.
- **Apply a Move mid-Turn at a step boundary, as OpenCode does.** Rejected: OpenCode runs the model loop in-process and can close its transport between steps; Shaman's Turns run inside external Provider processes with no boundary Shaman controls.
- **Have the Agent's `move_session` call block until its Session stands in the destination.** Rejected: the call's answer is owed to the very Provider process the Move stops, so it could only be stopping that process mid-call and resuming a conversation with a Tool call left unanswered, ending with it every other Tool call of that step, every Watch and every native Subagent a pending Move otherwise waits for. The Agent ends its Turn instead and is woken in the destination, below.
- **Let any Agent Move any Session.** Rejected: ADR-0042 keeps acting across Shaman to Sidekicks. An ordinary Agent Moves only its own Session and its brokered Subagents' Sessions, and only within its Workspace — beneath a Worktree of its Repository, including a new Managed Worktree, or beneath a directory-based Workspace's directory. A Sidekick Moves any Session anywhere. A native Subagent's Session is never Moved, since it runs inside its parent's process; a Sidekick's own Session is never Moved, since its Workspace is its identity.

## Consequences

- The glossary's Execution Directory is "set as the Session begins and changed only by a Move"; the first paragraph of ADR-0023 no longer holds where it says each Session retains its exact Execution Directory.
- A Move regroups the Session under the destination's Workspace in every Client viewing it, the Client's current Workspace follows, and a destination no Workspace knows gains a Workspace Registry entry as a Session beginning there would.
- A Move is an Activity of its own in the Transcript, Active while pending and settled when applied or failed, so a pending Move needs no state beyond the destination the Sidebar labels. One that waited is read where it settled rather than where it was asked, so what the Turn holding it went on to do reads before it; the Transcript's stored order, which only ever grows at its end, does not change.
- What holds a pending Move is whatever the Session's Provider process is running in the directory: a Turn of the Session's own, and any native Subagent Working beneath it, a running Agent inside that process. So does the Continuation owed once a native Subagent settles, or a Watch wakes the Agent, past its Turn, since the Provider is about to wake the Agent with that result and stopping the process would lose it from the conversation; it holds for a bounded while, a minute by default, because no Provider promises one and the Session reads as idle meanwhile. A Continuation that begins is an open Turn and holds the Move as any does. A Subagent that settled inside its Turn holds nothing, since that is almost always a result the Turn took in. A brokered Subagent holds nothing, having its own actor and directory to carry on in, and neither does a Watch still running. Interrupting stops all of it, which is how a user who will not wait makes a Move happen sooner. The Move applies once nothing holds it, with its destination read again, before anything begins another Turn: a Turn only owed begins behind it, in the destination, and Queued Prompts, Delegations and Reports wait for it while it is held. A stop leaves no later settling, so a Server starting settles every pending Move it finds. A Move replaced or cancelled settles Interrupted, saying why; a failed one settles Failed with its reason, and neither owes the Agent a note. Prompts left waiting are bound by name to the destination's Skills as the Move applies, and one that cannot be fails naming them.
- The Agent is told of the Move at its next Turn, as Provider input preceding whatever that Turn's input is, including that Subagents spawned before the Move still work where they were, so it spawns new ones for work in the new directory or Moves those it may. Nothing moves a child with its parent.
- An Agent that asks for the Move of its own Session is told, by the Tool's description and again by its answer, to end its Turn for the Move to apply, and is owed a Continuation once it has: Shaman starts its Provider in the destination and begins a Turn whose whole input is the Move's note, which says there that the Move was asked for from within the Session and that the work in hand carries on. This is the one Report Shaman starts a Provider to deliver, since the Move itself stopped the one that would have taken it. So an Agent Moves and carries on without the user, where before its work in the destination waited for the next Prompt. The Continuation is owed only where the Turn the Agent asked in completed, or the Session's latest Turn where none was open as a native Subagent's call asked, and nothing interrupted the Session since, so a user who stopped the work, or a Turn that failed, is not answered with the Agent at work again. Whatever Turn first carries the note to the Provider, a Prompt's that waited among them, carries the plain note at its head and the Continuation is owed no longer; a Prompt that fails before its Turn reaches the Provider carried nothing, and leaves it owed. Where the Continuation itself cannot begin, its Provider turned off or failing to start for it, it is given up rather than tried again, and the note waits for the next Turn. It is owed for the Move the Agent asked for and no other: one the user replaces or cancels meanwhile wakes no one, and neither does a Move an Agent asks of a Subagent, which never ended a Turn for it. What is owed is not stored, so a Server stopped before the Move applies settles it as it starts and wakes no one, as it wakes no one for anything else a stop cut short. A brokered Subagent that Moves itself is reported to its delegating Agent as its Turn settles and again as the Continuation does. A native Subagent's call taken for its parent's, on Claude and Copilot, is the parent's asking here too: the Subagent is told to end its Turn, and the parent is woken once the Move applies, which is why the note speaks of the Session rather than of what its Agent did.
- A Managed Worktree a Move creates is named before it is made — by an Errand reading the Session's Prompts so far, which the Move waits on for a few seconds and which leaves the Title standing, or else from the Session's Title — and started from the commit its previous Worktree stood at; its branch is never renamed afterwards. Its source commit is read as the Move is asked, so commits made afterwards, while a pending Move waits, stay on the old branch. In a Repository other than the one the Session works in, that previous Worktree's commit means nothing, so the Worktree starts from the commit the directory named stands at, a bare Repository's root included. One a Move leaves without a Session is Reclaimed eagerly, as one the last Session was deleted from is. Uncommitted changes are not carried.
- A draft Prompt's bound Skills are resolved by name in the new directory under the Worktree spec's rule, and the Skill Catalog is read from it.
- An Agent's Move needs no Approval; the Tool takes it no further than the Repository, and a Managed Worktree it creates is Reclaimable.
- The Server draws that boundary, from who the Broker knows is calling, before anything is read of the Session or made, and answers anything but the caller's own Session or one beneath it alike, whether it exists or what it is. It is read from where the caller's own Session works now, whichever Session is Moved: a Move applied has changed it, one pending has not, a Subagent working elsewhere has its own when it asks for itself, and a brokered Subagent is held to its caller's when its caller asks. Outside source control a Workspace is the directory it was read from, so what the Tool will take an Agent Moved beneath one to is beneath that; only the user's `/move` takes it back up. That boundary excludes any Repository beneath it, since a Repository's reach is wherever its Worktrees stand. A destination is judged where it resolves, and by the Repository source control says it lies in rather than by its path, so a Worktree standing anywhere is within it and a Repository nested in a Worktree is not.
- That boundary bounds what the Tool will do, not what an Agent can do. It is no sandbox, and Shaman does not run an Agent in one here. An Agent with a shell can `git worktree add` a Worktree of its Repository anywhere, which is then by definition within the boundary, can `git init` where it stands, and can work in any directory its Provider's own Tools reach. The boundary's use is to keep an Agent's Session grouped where the user put it unless the user says otherwise, and to tell the Agent so, not to contain one set against it.
- A destination is read once, and what is judged, remembered and stored is that one reading, whoever asked. A stored destination must be the destination: a Move whose directory has come to lead elsewhere, by a symlink standing there, is refused as it is read, and a pending Move whose destination has by the time it applies is failed saying where it now leads, rather than taking the Session wherever it does. So is one whose destination has come to lie in another Worktree or Repository than it did, or in one or none where it did not, since that would change the boundary the Session then stands within; a Worktree made again at its path, or whose branch was renamed, is the same Worktree. A boundary read from a Workspace directory that no longer reads as itself is refused too.
- A native Subagent's call of the Tool is what its Provider makes it. Codex names the Agent calling, so it is known and refused. Claude and Copilot name no Agent Shaman knows, so it is taken for its parent's, and Moves the parent, held until the Subagent settles.
- A Monitoring Session's Move stops its Provider process at once, so its Watches end as lost with that process and wake nothing. This is the one exception to ADR-0058, whose idle stop waits while Watches stand: a Move is the user's or an Agent's asking, and a Watch that may never finish must not hold it.
- Two things can still be lost, each knowingly. A background native Subagent settling inside a Turn, with the Provider waking the parent only after that Turn ended, is not waited for, since nothing tells it from a result the Turn took in without delaying every such Move. And output that has not arrived when the wait on a Continuation runs out is dropped with the connection; any already projected opened a Continuation, an open Turn, which holds the Move until it settles.
- A native Subagent's work therefore never ends with a Move, which waits for it; only a Subagent its Provider began in the moment between a Move applying and the process stopping is lost with that process, failed in words that say the parent Moved. Interrupting or a restart ends the others first, and their Sessions stay where they were.
- A native Subagent's Session left behind by a Move no longer references its Worktree, so it holds back no Reclaim: it cannot work on its own, and references a Worktree only through the Session whose process it rides. Once that Worktree is gone its Transcript still reads and nothing offers to recover it, since only a Session owning a Provider actor is ever prompted into a Worktree. A brokered Subagent's Session has an actor of its own and still counts.
- No Session Moves into the Sidekick Workspace, since any Agent working there is a Sidekick; a Move whose destination lies there is refused, as a Move of a Sidekick's own Session is. A Sidekick's Subagent is no Sidekick and may Move like any other Session, the ordinary Tool taking it beneath the Sidekick Workspace's directory, which is a Workspace of its own, and no further.
- A Sidekick's form of the Tool takes any other Session to any directory of its Server, where a Remote's own reading and judging of the path, its home and refusals included, is what ADR-0044 already makes of an act there. It must name the Session, since its own could only be refused. What ADR-0043 keeps from every Sidekick holds but for the exception above: a Subagent working in the Sidekick Workspace is its own Sidekick's to Move, and the user's, and any other Sidekick's, a Peer's among them, is refused it. This is the first exception of its kind among a Sidekick's acts: interrupting, settling or sending a Prompt to its own Subagent working there is still refused, since none of those takes the Subagent out of the Sidekick Workspace. A Sidekick's Move is recorded against its Session as its other acts are, here or carried to a Remote, unless it found the Session already there and changed nothing.
