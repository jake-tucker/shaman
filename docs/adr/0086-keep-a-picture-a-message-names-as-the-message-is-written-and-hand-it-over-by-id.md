# Keep a Picture a Message names as the Message is written, and hand it over by id

_Follows ADR-0085, which keeps a File Change's diff as a record of the edit and not of the file, and is held to ADR-0078 where it adds to what a Peer is answered._

An Agent shows its reader an image by naming a file in a Message: as a Markdown image, as a link's destination, or in a code span that is the file's path and nothing else. As that Message stops being written, the Server reads each file it names, once, and keeps the bytes beside the Session, as it keeps an Attachment's. The Message then says what became of each name, and a Client reads a kept Picture by its id over the route that already hands over an Attachment. No route reads a file by a path its asker gives.

The files an Agent points at are the ones least likely to last: a screenshot in a temporary directory, an image a Provider generated under its own home, a chart in a Managed Worktree that is later Reclaimed. A Transcript is a record, and a Picture read later would show the file as it had become, or nothing.

A link and a code span are names because an image is not what most agents write. [Run against the three Providers](https://github.com/jake-tucker/shaman/blob/ee21742318ec3c79b9408c26bda30482dac36264/docs/validation/0822-message-pictures.md), a GPT Model wrote an image where its reader asked to see a picture, in 35 of 37 Turns, and a link where it was only asked where the picture is. A Claude Model never wrote an image, under Claude or Copilot, in 75 Turns, and named the file in a code span. It is the Model's family that decides, and not the Provider.

- **Whose Messages.** An Agent's alone, a Subagent's among them in its own Session, and a Superseded Message's as any other's. A path written in a Prompt is never read.
- **Which files.** Any regular file the Server's user can read, wherever it stands, with symlinks followed. Nothing holds it to the Worktree or the Workspace. A device, a pipe and a directory are not read.
- **What counts as an image.** The four kinds an Attachment may be (PNG, JPEG, GIF, WebP), told by the file's first bytes and never by its name, and 10 MiB at most (10,485,760 bytes), whatever its size in pixels. That was an Attachment's 5 MiB until ADR-0088 raised it for every Picture; an Attachment stays at 5 MiB, which is what a Provider accepts from a user.
- **How a name is read.** By the Server alone, which knows its own platform. An absolute path is read as written. `~` is the Server's home, and `~user` is not read. A `file:` URL with no host, or `localhost`, is its path with the percent-encoding undone. A plain path is tried as written and then with its percent-encoding undone, where that differs. Any other scheme is never read, and one letter before a colon is a drive and not a scheme.
- **What a relative path is read from.** The Session's Execution Directory as the Message stops being written. Where no file is there, the root of the Worktree holding that directory. Where both hold one, the Execution Directory's is the Picture.
- **When.** Once, as the Message stops being written, however its Turn settled, so a Message cut off by an interrupt keeps its Pictures too. All of one Message's files are given five seconds together. Nothing is read again: a file that appears afterwards yields no Picture, and neither does any Message written before this.
- **How much.** The first 16 names of a Message, a name written twice counting once, and 20 MiB together. Images are taken first, in the order written, and then links and code spans, in the order written, so a list of files a Message mentions never crowds out a picture it shows. The same bytes named twice, in one Message or several, are stored once.
- **How the names are found.** The Server reads the Message as CommonMark, as the TUI does, and takes three things. Every image's destination, a reference-style one included. A link's destination, whatever its label. And a code span whose whole text, with the white space at its ends taken off, is a path. An image's syntax is itself the claim that its file is a picture, so every image's file is read. A link or a code span claims it by its name alone: it is read only where the name ends in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp`, in any case, and the first bytes still decide what the file is. A fenced or indented block of code is never read, nor a path written bare in prose, and a name with no directory is not searched for.
- **What the Message carries.** One optional list. Every image has an entry, under its name as it was written. A kept Picture's entry holds its id, its kind, its length in bytes and its width and height, so a Client holds its place before a byte arrives. An image not kept holds a reason: no file there, not an image of those kinds, too large, could not be read, or too many for one Message. A link or a code span has an entry only where its Picture was kept, and counts among the 16 only then; one that yields no Picture, for whatever reason, leaves nothing. Each entry says how it was named, as an image, a link or a code span, from an enum with a fallback for a kind a Client does not know. A name written more than one way has one entry, an image's where it is one.
- **What a name is.** What a Client matches an entry by. An image's or a link's is its destination as a CommonMark reader hands it over: backslash escapes and entities resolved and the angle brackets around one taken off, so not always the bytes the agent wrote. A code span's is its text as that reader hands it over, with the white space at its ends taken off. The Server reads with the parser the desktop app's Markdown view is built on, and that view passes a destination on untouched.
- **What a Client draws.** The desktop app draws an image's Picture where the image stands, at its own size, and an image not kept as a frame there saying why. A Picture named by a link or a code span is a tile under its Message, sized as an Attachment's in its Prompt, in the order named, and a press opens it as any Picture; the link stays a link and the code span stays as written. One Picture has one tile however many names found it, and none where the same Message already draws it at an image. An entry named in a way the app does not know is a tile. The TUI and the phone draw nothing from the list.
- **What a name with no entry is.** What it was written as: an image is a link, as a URL is, and a link or a code span is itself. That covers a Message still being written, a Message from before this, a link or a code span that yielded no Picture, and a Serving Server that does not yet keep Pictures, of which a reader is told nothing.

## Considered Options

- **Only an image's destination**, which is what was first chosen, before any agent had been watched. Rejected: it finds no Claude Model's picture at all, and a GPT Model's only where its reader asked to see it.
- **Telling the Agent how to show a picture**, in a sentence beside the Broker's note. Not taken for now. Tried on Claude alone, Opus wrote an image in 7 of 7 Turns and Sonnet in 3 of 7; nothing was tried under Copilot or Codex. It puts what one Client draws into every Agent's instructions, where the Server cannot tell which Client is reading. It could come later and change nothing here: an Agent that takes it up writes an image, which is already read.
- **The picture its Tool Call returned standing for the one a Message names.** A Claude Model asked to show a picture read the file first in 44 of 44 Turns, and ADR-0088 keeps what that returned. Rejected as the answer: it stands in the Turn's work, under a row a reader has to open, and from Claude it is whatever the CLI made of the file. Matching it to the Message's name would mean reading each Provider's arguments for a file's path.
- **Every link and every code span read, whatever its name ends in.** Rejected: a Claude Model writes every file, command and symbol in a code span, so the Server would open each one it could read as a path.
- **A frame for a link or a code span that yields no Picture.** Rejected: a Message that merely speaks of a file that is not there would draw a frame saying so.
- **A link's or a code span's Picture drawn at its own size**, as an image's is. Rejected: nothing tells a picture shown from one mentioned, and a Message listing ten files would draw ten.
- **A route that reads the file when a Client asks**, which is what was first chosen when deciding how pictures are shown. Rejected: it shows the file as it now stands or not at all, where the files in question are short-lived. The size is unknown until the bytes arrive, so a row jumps. A relative path has to be read from where the Session stood when the Message was written, which only the Moves in the Transcript can say. And a Peer would gain a route that reads a file by path with no Turn and no Approval, which then needs a rule about which paths.
- **Only files inside the Session's Worktree or Workspace.** Rejected: it refuses the commonest cases, a screenshot in a temporary directory and Codex's generated images under `~/.codex`. It protects little, since a Peer may already begin a Session under any Approval Posture and answer its own Approvals.
- **Reading as each name streams in.** Rejected: a name can arrive before its file is finished, and a Message is rewritten as it streams.
- **The bytes inside the Message.** Rejected as it was for a diff: a Client opening a Session is handed its whole Transcript, so every Client would carry every Picture.
- **The Client reading its own disk.** Rejected when deciding how pictures are shown: a Remote's file is not on the Client's disk.

## Consequences

- A Picture outlives its file. Deleting the file does not take the Picture out of the Transcript; deleting the Session does.
- A misled Agent can make any image its Server's user can read appear in its own reader's Transcript, and so be kept beside the Session. It goes nowhere else: a URL is never fetched, so nothing is sent to another host.
- The Server reads Markdown, which until now only a Client did. Where a Client's renderer sees an image the Server did not, it is a link; where the Server kept one a Client does not draw, the bytes are kept unseen.
- The Session database grows by the Pictures it keeps, bounded for each Message and not for a Session. Pictures nobody opens are kept all the same.
- The list joins what a Peer is answered and changes by addition only from then on. The reason is an enum with a fallback for a kind a Client does not know.
- The route that hands over an Attachment now hands over a Picture too, by an id that is the hash of its bytes and is scoped to no Session, as an Attachment's already is.
- The TUI and the phone are handed the list and draw nothing from it yet; the TUI keeps writing the name out.
- A picture a Message only mentions is kept and drawn as one it shows is, since nothing in a link or a code span tells the two apart. Asked to find a diagram, a Claude Model went on to name the repository's other picture in all 8 Turns. It costs a tile, and its bytes in the Session database.
- Some pictures are still not found. In 8 of the 74 Turns where a Claude Model had a picture to name, it wrote the file's name without its directory or did not name it, its reader having just typed the path.
- A file an Agent read and then named is kept twice, once under its Tool Call and once for its Message, wherever the bytes differ, as they do when Claude's CLI shrinks its copy. The viewer steps through both.
- What finds a picture rests on what each family of Model writes, which was seen on one version of each Provider and is read again when a Provider's pin or its default Model moves.
- A picture a Tool Call returned has a place to be kept in. ADR-0088 says how it is kept and carried, and shares this list's entry and its reasons.
- The limits (16 names, 20 MiB, five seconds) were chosen in conversation and never measured. Since a Picture may now be 10 MiB, 20 MiB holds two of the largest.
- A Client's cap on what it fetches by the Attachment's route rises to a Picture's 10 MiB.
