# Draw both Clients from one model, cut at what a terminal owns

_Follows ADR-0083, which made the desktop app a second executable whose crate never depends on the root package, and ADR-0080, which chose extraction over copy for the phone. Leaves the thin Client's core as it is._

The desktop app and the TUI draw from one model: the TUI's `Application`, taken out from under ratatui and crossterm into a crate both depend on. The cut runs at what a terminal owns. Everything that names no cell, no key press and no `Style` moves: a Server's answers, submissions and steers, the Provisional Session, Agent Selection, Interventions, the listing of Sessions, each picker's rows and filter, which surface is open and which part holds the keys, the plan of a Transcript with its Folds, Groups and Turn Folds, and the handling of semantic commands. The TUI keeps a terminal half around it: positions recorded as a frame is drawn, the pointer resolved against them, the keymap, wrapping, the Theme and render.

This was chosen because the model was nearer to it than it looked. `Application` already takes an event and returns one transition, calls no client, and funnels every key into a command before anything changes. What ties it to a terminal is what a window's own toolkit does for itself: hit-testing, selection, the caret, Markdown, wrapping and colour. And the line is one the compiler holds, since the shared crate cannot name ratatui or crossterm, where any line drawn through the meaning of the state would be a judgment made again for each of some 120 fields.

- **Two crates, and what each may not name.** `shaman-client-model` takes events and commands and returns transitions and readings. It names no ratatui, crossterm or Rune, no async runtime, and nothing that finds or starts a Server, so it builds wherever the thin Client's core does. `shaman-client-runtime` stands over it and `shaman-managed-client`, and holds what the TUI's event loop did besides the terminal: the streams, the effects a transition asks for, reconnecting and timers. It names tokio, and no terminal and no Rune.
- **The runtime drives a model it does not hold.** A window's toolkit keeps its state on its own thread, so the runtime cannot own the model there. It hands each event to its Client, the Client applies it to the model where the model lives and hands the transition back, and the runtime carries that out. The TUI does this inline in its loop. A Client also supplies what only its platform can do: the clipboard, opening a link, turning an image's bytes into something it can draw, and being woken to draw.
- **A view reads the model in place.** A reading is a function on the model that answers what a surface shows, in the model's own types: the Sidebar's entries, a Transcript's units with their keys, the Intervention to present. No layer of finished screens stands between, as one does for the phone, and no stream of changes by id, because no language boundary is crossed. The plan of a Transcript is memoized in the model; what is counted in wrapped rows, and its cache, stays in the TUI.
- **A Transcript is made of the same units in both.** Fold, Group and Turn Fold are words for a Transcript and not for a terminal, so a reader finds the same things folded in the window as in the TUI. How each unit is drawn is each Client's. A unit the window needs and the TUI lacks is a change to both.
- **The extraction goes surface by surface**, each step leaving the TUI's own suite passing untouched: the pieces already free of the terminal first, then the model's Session side with the TUI's `Application` left as a wrapper whose public API does not change, then the runtime. The first window is drawn there, and each further surface moves as the app reaches it. A surface the app does not yet offer stays in the TUI's half until it does.
- **Each layer is tested where it stands.** The model by events and commands in and transitions and readings out, with no Server and no runtime. The runtime against a real Server in process over loopback. The TUI's rendering suite stays where it is, as the proof that the TUI's behaviour did not change, and is not moved down wholesale.

## Considered Options

- **The TUI's model, cut at the Session**: only what a Server said and what the reader has asked of it shared, with each Client writing its own pickers, focus and command handling. Rejected: both Clients are driven by the same semantic commands, and those act on the pickers and the focus, so their handler and its state must be shared for that to be true. It would split the same file along a line nothing checks.
- **A model of the app's own over the managed Client**, sharing only leaf pieces. Rejected: it writes again the handling that joins a Session's events to its submissions and its Provisional Session, which follows a wire that moves daily. That is the second reader ADR-0080 refused for the phone.
- **The thin Client's core.** Rejected: its projections are pure functions of a snapshot, but its only entrance builds a redeemer and reads over a Pairing, its listing merges Remotes it has paired with, and it has no Agent Selection, completions, Attachments or usage. It is shaped for a phone's screens, one card to a Turn.
- **Bringing the thin Client's core onto the shared model in the same effort.** Not done: the core already re-derives the listing, a Turn's grouping, pending Interventions and the wording of an Approval beside the TUI's, and converging them changes what a shipped app shows. The model crate is kept free of Server-finding so that the core may take pieces of it later.
- **The whole extraction before any window.** Rejected: nothing would show whether the cut serves a window until all of it had landed.

## Consequences

- The app inherits the TUI's notion of which part holds the keys, and reconciles it with its toolkit's own focus by rank. The model says which surface holds the keys (the composer, the Sidebar, the Aside, an Intervention, whatever stands over the window, and in the desktop app the Transcript, whose rows the TUI leaves to the pointer), since it decides what a command means there and what is refused; the toolkit's focus says which control inside that surface. The app keeps the two in step: where the model moves the keys it sets the toolkit's focus, and where a press, Tab or F6 carries the toolkit's focus into another surface it tells the model with a command. A key is resolved to a command from the surface the model names.
- What the model is handed about its Server, such as that it is recovering, is defined beneath anything that finds a Server, and the few things the model read from the root package come down with it.
- The command catalog names its key bindings in a chord type of its own. A command that has a key in a window declares that chord beside its terminal binding, written against a primary modifier (⌘ on macOS, Ctrl elsewhere) with an override per platform, so that a palette, a menu, a tooltip and a button all say one key; the app turns it into its toolkit's type. A window has no Leader: a toolkit's chord is one key with modifiers, and Ctrl+X is cut off macOS. The keys of one surface, such as those that walk a list, stay with each Client, as the TUI's keymap does. Commands that carry a position on screen stay the TUI's, and a window asks for the same acts by the row they fall on.
- The command catalog also says what a palette and a menu bar offer, so neither is a list written by hand. A command declares whether it is listed, the group it is listed under, and the one kind of Client that offers it where it is one alone; a group orders a palette and names the menu a command sits in. Whether a listed command can act as things stand is one reading of the model, which answers that it can or says why in a sentence, so a palette's dimmed row, a menu's dimmed item and the refusal of a key or a slash command all agree, and a listed command no longer does nothing in silence. Where a listed command's title follows state, as showing and hiding do, the model says which title holds. Matching what a reader types against the catalog is the model's as well, so a slash command's completions and a palette rank alike.
- An event no longer carries an image already encoded for a terminal: a Client is handed the bytes.
- The model's composer holds a draft's text and what is bound into it, as spans over that text, with the draft's history and the numbers its labels have reached. Editing a draft key by key, with the caret and the selection that takes, is what a terminal has to do for itself and stays the TUI's. A window's toolkit has an editor of its own, which holds a draft while it is edited and hands the model its text and spans at each change; the model hands a draft back where it changes one itself, as recalling an earlier Prompt does. A label is one unit in that editor, a Skill Invocation's included, so an edit never reaches inside one there, where in the TUI an edit inside `$name` unbinds it.
- Until every surface has moved, the TUI's wrapper holds events and state of its own beside the model's, and a reader of it finds two places a surface may live.
- Some of what the runtime does waits on a frame having been drawn, such as claiming a notice once it could be read, so a Client tells the runtime when it has drawn.
- `tests/tui_rendering` reaches the model only through the TUI. A fault in the model that the TUI's rendering hides is caught only by the model's own tests, which begin empty.
