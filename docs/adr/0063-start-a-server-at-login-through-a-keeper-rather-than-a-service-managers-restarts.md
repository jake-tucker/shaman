# Start a Server at login through a Keeper rather than a service manager's restarts

A Server outlives its Clients (ADR-0001), but nothing started it, so a rebooted machine stayed Unreachable until someone ran Shaman on it. `shaman server install` now registers, for one Channel, a user-scoped start with the machine's own service manager: a LaunchAgent on macOS, a systemd user unit on Linux, a Scheduled Task at logon on Windows. It is off until asked for, and asks for no elevation.

What each runs is a **Keeper** (`shaman __keep-server`), a small foreground process that lasts the login. It launches the Server exactly as a Client launches one, detached, then reads two things every few seconds: the Channel's election lock, and its last-stop record. With the lock held there is nothing to do. With the lock free and a Manual stop recorded since the stop it follows, it launches nothing, because that stop is final (ADR-0002). A stopping Server records its stop before it lets the lock go, so a Keeper finding the lock free has already seen any record that would tell a stop from a crash. With the lock free on consecutive looks and no such record, the Server crashed, and it launches another. A Server it finds standing after a stop, because someone started the Channel again, puts that stop behind it. The Channel's election and last-stop record stay the one authority on all of this; the Keeper only reads them.

No registration asks its service manager to restart anything: not `KeepAlive`, not `Restart=`, not `RestartOnFailure`. A restart runs the Keeper afresh, and a Keeper run afresh takes the Channel's last stop as already seen, which is what a new login must do and what a restart must not. It is the same reason exit codes play no part. A Server exits nonzero having lost an election, and with the cutoff's status if its stop ran over (ADR-0002), and exits zero on being replaced, so a policy keyed to its exit would both restart Servers its user had stopped and loop on an election it can never win. launchd throttles what it restarts, systemd gives up past a start limit, and what Task Scheduler's restart answers is not something to lean on, so the three would have behaved three ways. One Keeper behaves one way, and is tested against real Servers on every platform with no service manager in sight.

Registering and removing take effect at the next login and touch nothing running. On macOS that is only the plist: launchd reads the directory at login, so neither `launchctl bootstrap`, which with `RunAtLoad` would start a Server its user may have just stopped and which needs a login at the screen to exist, nor `launchctl bootout`, which ends the job, is ever run. On Linux it is `systemctl --user enable` and `disable`, without `--now`, with `KillMode=process` so that nothing stopping the Keeper reaches the Server sharing its control group. On Windows it is `schtasks /Create /XML` and `/Delete`, and the Server is launched detached from what the Task started, which should put it beyond what ending or deleting a Task reaches; that has yet to be seen on a real Task Scheduler. A Keeper still running as its registration goes launches nothing further and ends. `shaman server start` remains the way to have a Server before that login.

A Keeper replaces a Server of another build only as it sets out, as any Client does (ADR-0001). After that it never compares builds, so it cannot fight the Client that replaced one, and an upgrade at the registered path is simply what the next launch runs. The registered path is the one that lasts: where this binary's own path looks passing, as a Cellar directory does, a `PATH` entry leading to the same binary is named instead, and where none does, install warns.

Providers are found on `PATH`, and launchd, systemd and Task Scheduler give far less of one than a shell. The registration carries `PATH` captured as `shaman server install` runs, with the variables that name a Provider's executable (`SHAMAN_*_PATH`) and that move where a Provider or its config lives (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `COPILOT_HOME`, `XDG_CONFIG_HOME`), on the Keeper's own command line, so all three service managers are told one thing and the Scheduled Task, which has no way to set an environment, is told it as the others are. It goes stale until the next install, and install says so. Nothing else is carried. API keys and proxy settings may hold secrets and a file under a home directory is no place for them, so install names those it finds set, and a Provider signed in only through one needs another way in.

This is a start at login rather than at boot because of ADR-0050: a Mac's login keychain opens at that login, and on Linux a keyring may not answer before one. Where the store does not answer, the Server already serves its own machine, fails Serving where the user can see it, tries again at the next use, and never mints a new key. Install says plainly what each platform covers, and `loginctl enable-linger` is what lets Linux run with no session.

## Considered Options

- **Run the Server itself under the service manager, with a restart-on-failure policy.** Rejected as above, and because removing the registration then ends the Server on macOS, and restarting a job takes the Server down with it. It would also make a supervised Server unlike every other one, needing an exit-code contract the election has never had.
- **Hold a Server open through a managed client's lifecycle stream, as a Client does.** Rejected: a stream speaks a protocol, so a Keeper left running across an upgrade would be a Client of an incompatible Server. The lock and the record are the ones whose shape already outlives a build.
- **Resolve `PATH` from a login shell each time a Keeper starts.** Rejected: it runs the user's shell startup files unattended at every login, which may prompt, hang, or start things, and can fail in ways nobody is there to see. Capturing at install is simple, visible and refreshed by running it again.
- **Capture the whole environment.** Rejected: it would write every secret a shell holds into a file under the home directory.
- **Pass the environment through each service manager's own means.** Rejected: a Scheduled Task has none, and it would be three quotings of one thing rather than one.
- **Install starting the Server, or `--now`.** Rejected: a stop must stay stopped until the next login or an explicit start, and `shaman server start` is that start, with no second way to ask for it.

## Consequences

- A Keeper is one more process per registered Channel, looking at two files every five seconds. A crashed Server is back in about ten.
- Killing a Keeper by hand ends its restarts until the next login, and the Server carries on. There is deliberately nothing to restart a Keeper, since that restart could undo a stop.
- A Server started by a Client after a crash, or by `shaman server start` after a stop, is kept like any other for as long as a Keeper runs. A Keeper reinstalled with a different path goes on launching the old one until the next login.
- `shaman server status` says whether a Login start is registered, and exits as it always did by the Server's own standing, not the registration's. It reads what was registered and nothing of whether the service manager will run it, so it reads registered through a Login Items toggle, `launchctl disable`, a disabled Task or a masked unit.
- A Keeper's command line is a persisted interface. The plist, unit or Task holds it until the next `shaman server install`, whichever build is at the path by then reads it, and a build renaming a flag would fail at the next login with nothing to show for it, while `status` says registered. So its flags are pinned by `a_keepers_flags_are_spelled_as_registrations_have_them`: a new spelling is added as an alias, and an old one never removed. It does not itself fall under ADR-0047, which covers the Relay, but it is held to the same care.
- `shaman server stop` stands even with no Server there to answer it, one having just crashed or crashing each time it is launched: it records the stop under the Channel's lock, as ADR-0002 now has it, and a Keeper holds to that as to any other.
- A plain `kill` of a Server is a signal answered as a Manual stop (ADR-0002), so it is not restarted, and only something like `kill -9` reads as a crash. A hung Server, stopped with SIGSTOP say, is not restarted either: it holds the election, so a Keeper has nothing to answer, and `shaman server stop` fails as unreachable because nothing may be recorded past a lock it holds. Both were so before this.
- Logout ends things differently per platform. On Linux with no linger the user instance signals the Keeper alone, and the system then kills what is left in `user@.service`, so the Server goes as a crash leaves it with no stop recorded: `KillMode=control-group` would kill the Server whenever the Keeper ended, and `ExecStop=` also runs after a Keeper has ended by itself, so neither is a clean way to do better. On Windows logging off is delivered only to services, so a Server ends the same way. What macOS does to a detached Server at logout is not verified. Whichever it is, the next login's Keeper finds the Server standing or starts another, so exactly one runs after.
- On Windows a Keeper may read its Task as gone, and end at the first crash, where a Task made from an elevated prompt turns out to be invisible to it unelevated. A Task's name also holds the machine's name, so renaming the machine leaves it behind where `status` and `uninstall` no longer find it. The first is not verified; both are in `docs/validation/0608-login-start.md`.
- On macOS a Server under launchd may count as its own program to the privacy checks rather than as part of a terminal, so work in Documents, Desktop or Downloads may raise a consent prompt with nobody there to answer it. This is not verified either, and `docs/validation/0608-login-start.md` has a step for it.
- On Windows a console window may show for a moment at logon, before the Keeper lets it go.
