# Put a thin Client's protocol code in a Rust core shared with the Server

_Follows ADR-0077, which made a thin Client an ordinary Peer, and ADR-0078, which holds what a Peer and a Serving Server say to each other to compatibility. Leaves the rule that a mobile app's UI is built with its platform's native frameworks as it is: that rule is about UI, and this decides what lies beneath it._

Everything a thin Client does beneath its screen is written in Rust and shared with the Server and the TUI: redeeming an Invite, holding a Pairing, carrying it directly and through a Relay, the Relay conversation and its login, decoding the Session API, reading it tolerantly, reconnecting its streams and applying a Session's updates to a snapshot. The iOS app is SwiftUI over that core. This was chosen because the wire moves about once a day (44 protocol versions between 2 October and 16 November 2026, 28 of the last 45 touching something a phone reads), and ADR-0078's rules for reading what a reader does not know are reader code the TUI needs in Rust whichever way this went. A second decoder and a second projection in Swift would have to follow each of those changes by hand, and where they fell behind the fault would be a wrong Transcript, not a build that fails. In Rust a change to the wire lands once, and the test that runs one release against another covers the phone's reader because it is the TUI's reader.

- **The core is the thin Client minus its screen.** It holds the Remotes and their records, the Relay entries and Logins, dialing and keeping up, the Outlook, and the merging of several Remotes' Sessions into one listing. Swift hands it a directory in the app's container, a way to sign with the identity key, and news of the app's lifecycle. Swift keeps what only the platform can do: scanning an Invite, the sheet a login is approved in, and its own Settings screens.
- **What crosses to Swift is a model shaped as what the phone shows**, not the wire's types: the Session list as rows in order, a Transcript as messages and one card for each Turn's work, the state of live work, the Intervention to present, and an Activity's detail by kind. The wire's types stay inside Rust, so a change to the wire that the phone does not show never reaches Swift, and the placeholder ADR-0078 gives an unknown kind of Activity is one more kind of row. Grouping is a function of a Session's state and is tested where the rest of the core is, with no simulator.
- **The binding is UniFFI**, by its macros, pinned to an exact version and confined to one crate, so nothing else in the core knows of it. UniFFI has no streams and no cancellation, so each stream crosses as a listener and a handle that cancels it.
- **The code is extracted and shared, not copied.** The Server's redeeming side and the core link one pairing client and one Relay client. The TUI's Client and the core share one set of stream readers and Session commands over a transport that is either the machine's own Server on loopback or a Pairing. Finding, starting and keeping a local Server, and everything of its administration, stay where they are.

## Considered Options

- **Native Swift throughout**, on swift-nio, swift-nio-ssl and swift-nio-http2. Rejected: about 176 types to mirror, 28 of them enums that need decoding written by hand, a second projection and a second tolerant reader, each kept in step with a wire that moves daily. It would not have been Apple's networking either, since no TLS of Apple's runs over bytes an app supplies and a Relay way needs exactly that.
- **Rust for pairing and transport, Swift for the Session API.** Rejected: it pays for a binding and still writes the second decoder and projection, and it shares the half of the wire that seldom changes while duplicating the half that changes most.
- **Swift types generated from the wire's schema.** Rejected: it removes the mirroring and leaves the second projection and the second tolerant reader.
- **Handing Swift the wire's own types through the binding.** Rejected: the Swift the binding generates would change with every change to the wire, and a new variant would break each place the app handles every case.
- **A copy of the Pairing code for the core, reconciled with the Server's later.** Rejected: it gives up the reason for choosing Rust.
- **A binding with streams built in, or one written by hand over C.** Rejected: the one generator found that has streams is under a year old with no app found shipping it, and a hand-written binding is what a team maintains. UniFFI also generates Kotlin from the same crate.

## Consequences

- The core cannot be built until the redeeming side of a Pairing comes out of the Serving side's controller, the Relay client comes out from beside the Server's own Relay list, and a transport stands under the Client's stream readers and Session commands, which today reach a loopback address at 49 places and reconnect by the local Server's instance. Nothing before this let a Client speak a Pairing without a Server of its own, so the last of those is new design and the largest piece of work this creates. It comes before any app code.
- The core dials with plain sockets, so it reads no proxy from the device's network settings on the way to a Relay, a dial does not bring up a VPN set to connect on demand, and a refusal of the local network arrives as a bare error, so the app hints at it whenever every way that failed was a local address. A Relay way still runs over a byte stream the core is handed, so the platform could supply that connection later.
- The boundary between Swift and the core carries no promise of compatibility: both ship in one app from one commit. The promise of ADR-0078 is the core's to keep, as a Peer.
- A thin Client's Pairings are kept in the Server's record shapes by the same code, and are carried forward with it.
- A change to what the phone shows that needs something new derived from a Session is a change in Rust and a regenerated binding before it is a change in Swift, and building the app means building for two toolchains.
- The short code, the offer to pair back and the rendering of a Session as text for an Agent stay out of the core; a thin Client uses none of them.
- An Android app would link the same core and bind it through the same crate. That was a benefit of this choice and not the reason for it.
