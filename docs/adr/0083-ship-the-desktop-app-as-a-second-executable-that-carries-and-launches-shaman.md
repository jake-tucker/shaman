# Ship the desktop app as a second executable that carries and launches `shaman`

_Narrows ADR-0077's "a later desktop app is one kind or the other by where it is installed": the desktop app is never a thin Client, and is installed only where a Server is. Leaves ADR-0001's build matching, ADR-0050's signing identifier and ADR-0063's Keeper exactly as they are, which is most of why it was chosen._

The desktop app is an executable of its own that holds a window and no Server. Each release of it carries the `shaman` of the same release, inside the bundle on macOS and beside the app's executable on Windows and Linux, and the app launches that one as its Server, found from its own executable's path and never from `PATH`. `shaman` stays what it is: the TUI, the Server and the Keeper. A Client already reads the build of the executable it would launch and compares it with the running Server's (ADR-0001), so with the app pointed at the `shaman` it carries, the TUI, a Keeper and the app compare one build and share one Server, and none replaces another's. Nothing in the launcher changes.

This was chosen over one executable for what one executable costs on each platform. On Windows an executable has one subsystem: as a console program it shows a console window when opened from the Start menu, and as a windows program the shell does not wait for it, so the TUI cannot own its terminal. On macOS a bundle's signature lives in its main executable, so one program offered both bare and as an app is two signed files, and the bundle's main executable would have to be signed as `ai.shaman.cli` against a bundle id of its own for the keychain to go on trusting the Server. And every `shaman`, a headless Server's included, would carry a GPU renderer it never draws with, or a cargo feature would leave two configurations to keep passing on three platforms.

- **One install, one release.** The loopback wire matches exactly and moves about once a day (ADR-0080), so the app and `shaman` are never installed apart. Where the app is installed it is the whole of Shaman on that machine, and `shaman` on `PATH` leads to the one the app carries. The file a release puts in the app is the file it publishes bare, signed once, so a bare install and an app of one release are one build. Two releases on one machine are not supported and behave as two installs always have: each replaces the other's Server as it starts.
- **What a reader is told when they differ.** The app's own start cannot meet another protocol, since it replaces a Server of another build with the one it carries. An app left attached while a `shaman` of another release replaces its Server says which of the two is the older and which to update, never a version, and does not replace the Server back. The TUI's messages are held to the same rule.
- **A Keeper is always `shaman`.** The app's executable answers neither `__server` nor `__keep-server`, and a Login start registers `shaman` and never the app, whichever of the two asked for it.
- **A Server the app starts is given a shell's environment.** An app opened from Finder or a desktop launcher has no shell's `PATH`, and a Server finds its Providers there. Where the app must start a Server on macOS or Linux and none of its standard streams is a terminal, it asks the user's shell for its environment at each start it makes, under a timeout: as a login and interactive shell, which is what reads the files a version manager is set up in, and as a login shell alone where that fails. It hands the Server the whole of the answer laid over its own environment, and where neither answers it hands over its own and says so. ADR-0063 rejected this for a Keeper because nobody is there at login to see a shell hang or prompt. Here someone has just opened the app, nothing is written down, and a Server the app starts is then the same as one the TUI starts.
- **The app starts no Server from a path that does not last.** A Server outlives the window, and a Mac may run a downloaded app from a randomised path or a mounted disk image. From such a path the app says to move it and does nothing more. `shaman server install` already knows a temporary directory when it weighs a path to register, which covers the randomised path; a mounted disk image is new to it, and a directory named for a version, which it also distrusts, is no reason for the app to refuse.
- **The app's crate never depends on the root package.** Finding, starting and keeping a local Server moves out of it into a crate both depend on, beside the readers and commands ADR-0080 already took out. The app's crate is a workspace member and not a default one, so linting, testing and releasing `shaman` build none of the window.

## Considered Options

- **One executable for the terminal and the window.** Rejected as above. It would have kept one thing to install, which carrying `shaman` in the app keeps anyway.
- **Two executables, each holding a Server.** Rejected: neither's build equals the other's, so each start of one replaces the other's Server, unless build matching learns what a release is, and the Server would ship twice.
- **The app finding a `shaman` installed apart**, where the install scripts put it and then on `PATH`. Rejected: two installs would have to be kept at one release by hand against a wire that moves daily, someone who downloaded only the app would have nothing to start, and an install directory of the user's own cannot be found from Finder.
- **Holding the loopback wire to compatibility, as ADR-0078 holds a Pairing's**, so that the two could be upgraded apart. Rejected: that cost was taken on because a phone and a Server cannot be updated together. Two files in one install can.
- **A marker both executables carry, compared as the app starts.** Rejected: it would mean something only where both were compiled in one invocation, which is what development does not promise and what a release already guarantees by its packaging.
- **Carrying only `PATH` and the variables that find a Provider, as a Login start does.** Rejected: there is no install step to capture them at, and a Provider signed in through a key in a shell profile would work in the TUI and not in the app.

## Consequences

- `PROTOCOL_VERSION` is the only check between the app's own code and the Server it attaches to, where the TUI and its Server are one build. In a release their packaging makes them one release. In development the app finds whatever `shaman` was last built beside it, so the two are built together by a script, a missing `shaman` is an error that names what to build, and a change to the loopback wire that forgets to move `PROTOCOL_VERSION` can go unseen there as it cannot in the TUI.
- On macOS `shaman` is nested code in the app's bundle, signed by itself as `ai.shaman.cli` before the bundle is signed under an id of its own. That the keychain trusts it there as it trusts the bare binary, and that notarization accepts it, are not yet seen with a Developer ID.
- On a Mac's case-insensitive disk an app named Shaman and `shaman` cannot both sit in `Contents/MacOS`, so one of them is named or placed otherwise.
- Linux ships no AppImage: its executable lives on a mount, which is a path that does not last.
- On Windows the app is a windows-subsystem executable in release builds, and a console one in debug builds so that its headless flags still print.
- A release builds, signs and publishes two files where it published one, and both install scripts, which copy `shaman` and look for a running one before replacing it, learn of the app.
- The first cut opens the window from the platform's launcher alone. A typed way to open one, and to hand a Workspace to a window already open, is left for later.
